# Recipe: derive a map's loading poster from its own current build

Owner rule HF-481: written so someone building a DIFFERENT level next month can
apply it without rediscovering it.

## Problem

Hand-authored loading art goes stale the moment the map changes, and "update it
every pass, for all maps" by hand is a chore nobody does reliably. The fix is
to derive the still from a capture of the map at the current build, inside the
pass, with a gate that fails when nobody ran the derivation.

## What the loading surface actually paints

- The deployment loading screen (`#deployment-transition`) paints the poster
  `public/assets/original/menu-previews/<arena>.webp` plus the shared menu
  `<video>` element (`prepareDeploymentTransition` in `src/legacy-main.ts`,
  via `src/ui/deployment-console-surface.ts`).
- The "start video" is a real video file: an 8 s prerecorded flyover
  (`<arena>.webm` / `<arena>.mp4`, 2560x1440) with the `.webp` as its poster
  and reduced-motion fallback (`src/ui/menu-preview-video.ts`). Regenerating
  video every pass is a larger problem (240-frame capture, encode, cache
  families, review sheets) — scope the still first.

## Instrument

```sh
# Capture ONE station at poster resolution through the unmodified viewpoint instrument:
node scripts/generate-loading-poster.mjs --arena <id> --url http://127.0.0.1:<lane-port>
# Then install (explicit step, never implicit):
node scripts/generate-loading-poster.mjs --arena <id> --url http://127.0.0.1:<lane-port> --install
# The gate (exit non-zero on stale):
node scripts/check-loading-art-freshness.mjs [arena...]
```

The script calls `scripts/qa/capture-arena-viewpoints.mjs` with
`--arenas <id> --cameras <station> --samples 1 --viewport 2560x1440` — one
station, one sample, native poster resolution, no edits to the instrument.

## Camera rule

Curated table (`REPRESENTATIVE_CAMERA`) with a first-roster-entry fallback,
recorded in the sidecar. Prefer the widest authored view that shows the map's
defining space; never an interior, a close-up, an into-sun exposure probe, or
a top-down plan. nuketown2's first station is an overhead, so it curates to
`nuketown2-street-centre`.

## Encoding (invents nothing)

Single-frame libwebp at the retained masters' profile, read from
`source-assets/menu/pass65-preview-masters/choreography.json`
(`media.encodingProfiles.images.posterQuality` = 88,
`media.encodingBudget.maximumPosterBytes` = 1.5 MB):

```sh
ffmpeg -y -i <station>.png -map_metadata -1 -frames:v 1 -c:v libwebp -quality 88 <arena>.webp
```

Probe before install: codec webp, 2560x1440, within budget.

## Provenance + gate

Sidecar `public/assets/original/menu-previews/<arena>.loading-provenance.json`
records arena, camera (+ whether curated), source SHA, capture frame SHA, and
output SHA/bytes. The gate fails on: missing sidecar (art predates the
pipeline), source SHA != HEAD, poster bytes drifted from the recorded SHA, or
missing poster. A check never seen to fail is not a check — demonstrate all
three reds against `--root` fixtures before trusting a green.

## Failure modes avoided

- Flat-frame capture: the capture verdict (including its flat-frame gate) must
  be PASS or nothing is staged. Never lower that floor.
- Dirty tree: the generator refuses unless
  `git status --porcelain --untracked-files=no` is empty, so the sidecar SHA
  always names the bytes that were captured.
- Cache staleness: regenerated bytes ship under the arena's existing `?v=`
  cache key, so mint a new cache-family key at publish time if the poster
  changed (same rule the menu-preview families follow).
- Contended GPU: same heavy-lock protocol as capture lanes
  (`%TEMP%/aa-heavy.lock` + owner.json, 20 s poll, 4 GiB floor, never take
  over, release in a trap). Budget one capture per candidate.

## Upstream links

  no upstream API beyond `renderer.domElement.toBlob` / CDP capture. The
  technique here is pipeline (deterministic review camera + receipt +
  provenance), not rendering.
- Repo instruments reused, not modified: `scripts/qa/capture-arena-viewpoints.mjs`,
